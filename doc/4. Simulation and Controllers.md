# 4. Simulation and Controllers

The simulator advances household energy flows in 15-minute intervals. At each interval, a controller chooses how much power to send to the electric vehicles (EVs) and whether to charge or discharge the stationary battery, when present. The simulator applies those decisions and records the resulting state.

## 4.1 Simulation

`main()` in `simulation.py` reads the household IDs, scenarios, and controllers selected on the command line. A `RunContext` pairs a controller with a scenario. For each selected household in that context, `Simulation` builds the household and its devices, then loads its daily profiles from SQLite.

The daily input profiles contain 96 quarter-hour periods. Each simulation step follows the same sequence:

1. Set the current period and update the household inputs.
2. Call `controller.set_controls(household, scenario)` to compute the control actions.
3. Apply those actions to the household for the current interval.
4. Record the updated state in the household history.

After each household run, the simulator writes the history and run metadata to `results.db`.

`Household` groups the device models and exposes their current state and the household history to the controller. The device models represent the equipment described in Chapter 2, including battery charge levels and EV availability.

## 4.2 Controllers

All controllers implement `set_controls(household, scenario)`. The household supplies the current state and history. The scenario defines requirements such as target states of charge (SOC). The method returns a charge or discharge setpoint for the stationary battery, when present, and a charging setpoint for each EV.

### 4.2.1 Waterfall

Waterfall is the rule-based baseline. It chooses actions from the current state using a fixed set of rules, without forecasting future inputs.

### 4.2.2 Model Predictive Control (MPC)

At each step, MPC uses the current state and forecasts of future inputs to plan a sequence of control actions. It minimizes net electricity cost over the planning horizon subject to device limits, EV charging availability, and scenario SOC targets.

The simulator applies only the first action. At the next step, the controller solves the problem again with the updated state and forecasts. Keeping the horizon length fixed preserves the dimensions of the optimization problem and allows the solver to warm-start from the previous solution.

### 4.2.3 Forecasting

The same MPC approach can use different predictors:

- **Oracle** uses the actual future inputs as a perfect-foresight reference.
- **Historical average** provides a simple forecasting baseline for measuring the value of learned forecasts.
- **Recursive single-step XGBoost** predicts one step ahead and feeds each prediction back into the model to extend the forecast.
- **Multi-step XGBoost** uses a shared model for several forecast horizons.
- **Multi-model XGBoost** uses a separate model for each selected forecast horizon.
