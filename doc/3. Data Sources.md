## 3. Data acquisition and preparation

The original dataset is stored in a SQLite database and combined with external profiles for load, PV, and EVs.

## 3.1 Original dataset and database structure

### Origin

We mostly rely on the dataset from [this paper](https://www.sciencedirect.com/science/article/pii/S2352340923003372?via%3Dihub) from june 2023.

Everything is stored in an [Excel workbook](data/dataset_original/EC_EV_dataset.xlsx). Table Descriptions can be found in [the General Description](/data/dataset_original/General%20description.docx)

`src/ingestion/table_loading_original.py` reads the relevant 
Excel ranges and writes the source tables to
`sqlite/source_original.db`.

The original database is then copied as `sqlite/source_runtime.db`, where profiles for base load, PV and EVs are replaced with new consumer data.

### Format

The original Excel file contains technical lookup-tables as well as 96-step time series data.

Time series are stored as wide tables, with one `period` column (1-96) and columns `"1"` through `"250"` for the day profiles of each household.

### Filtering

The consumption data is stored as a set of CSV files, one per household ID.

We keep households with installation type `'Single-family house'` that have at least 70.000 data points, where all of these metadata flags are false:
`1_ewh`, `1_hp`, `1_hp-add`, `1_hp-wh`, `1_ev`, `1_storage_heating`,
`1_direct_heating`, and `1_change`.

The column `kWh_to_installation` is multiplied by 4 to convert the energy to average power in kW for the 15-minute intervals.

These values are then used to create a wide `load` table in `sqlite/staging/CH_loads.db`.

Day profiles are valid for runtime and training pools if the total energy as well as the peak load are within the ranges of the original profiles.

Days with any missing datapoints are filtered out.

The selection of the 250 replacement load profiles aims to not change the contractual power level (CP) of the consumers from the original dataset, in order to preserve the balance of the simulation energy flows.
So for each household we determine the allowed range for its peak load, based on the table `General Information -> Contractual Power Term` in the [EC_EV_dataset.xlsx](/data/dataset_original/EC_EV_dataset.xlsx).

40 of the 81 CH load households with valid peak loads are then used to replace the original profiles.
The selection is spread out so that per household, 6 or 7 end up in the simulation data.

No further scaling is applied.

All time series from the remaining household IDs are kept in the training database; the current pipeline does not select 1,000 individual load-days.


## 3.2.2. PV Data

### Source

We use household PV generation data from [Open Power System Data](https://data.open-power-system-data.org/household_data), covering 2014-12-11 to 2019-05-01.

The source data is stored in `data/dataset_DE_PV/pv_data_non_empty.csv`. It contains four residential PV systems: `residential1`, `residential3`, `residential4`, and `residential6`.

### Filtering

The source values are cumulative meter readings. To get power for each 15-minute interval, consecutive readings are differenced and multiplied by 4. Negative differences are set to zero, and the first value is set to zero. The resulting data is stored as a wide `pv_gen` table in `sqlite/staging/DE_pv_gen.db`, with values in kW.

For each system-day, metadata is calculated only when all 96 periods are present. Days whose maximum generation is at most 0.05 kW are excluded. A day is added to `pv_gen_pool` when it has between 46 and 54 periods with generation above 0.05 kW. The pool also stores a `shift_periods` value intended to center the generation window around period 62, and excludes shifts that would move the active window outside the day.

The stored profile values are not actually shifted when the profiles are copied into runtime or training data.

### Runtime and training selection

For runtime, all `residential3` days in 2018 that are in `pv_gen_pool` are selected in date order. The selected daily profiles are assigned in order to the households with PV in the original dataset. If there are more target households than selected days, the days are reused from the beginning. Each profile is multiplied by 0.8 to match the average power generation of the original dataset; no matching by the original household's generation or energy is applied.

For training, `residential3` is excluded. The other three systems are included only on dates where they have a day in `pv_gen_pool`, and only before 2018. Their generation values are also multiplied by 0.8.

## 3.2.3. EV Data

### Source

We use the VISTA travel survey data ([paper](https://pmc.ncbi.nlm.nih.gov/articles/PMC11462014/), [data](https://data.mendeley.com/datasets/gphwn7sy5n/1)), stored as `data/dataset_VISTA_EV/T_VISTA1218_V1.csv`.

Two types of daily travel profiles are created: EV1 represents a work commute with a trip to work and a return trip home; EV2 represents a chain of casual trips during the day.

### Filtering and staging

For EV1, we keep vehicle-driver trips marked `Work Related` that match the expected commute: the first trip is from `Survey Home` to `My Workplace`, and the second is back home. The trips must fall within the specified morning and evening time windows, and only people with both trips are retained.

For EV2, we keep vehicle-driver trips that are not work-related, education, or pick-up/drop-off trips, and that arrive before 22:00. A person's trip chain must start at `Survey Home`, have consecutive trip numbers starting from 1, and end with the destination purpose `Go Home`.

The scripts create a 96-period daily status profile for each person. Status is `0` at home, `1` while driving, and `2` while away from home (at work or another destination). Trip times are rounded to 15-minute periods. Trip distances and the `PERSID`-to-`HHID` mapping are stored alongside the status data in `sqlite/staging/VISTA_ev1_status.db` and `sqlite/staging/VISTA_ev2_status.db`. EV1 status is wide (one column per person); EV2 status is long (`PERSID`, `HHID`, period, status).

### Runtime selection and profile creation

For EV1, the 250 runtime profiles are selected with `random.Random(42)`. The 38 people belonging to shared VISTA households are prioritized, then the remaining profiles are shuffled and used to fill the player slots. This results in 250 people from 231 distinct VISTA households.

For EV2, the candidate list is sorted by `PERSID`, shuffled with seed 42, and selected so that each of the 250 runtime profiles comes from a distinct VISTA household. The selected `PERSID` and `HHID` mapping is saved in `source_runtime.db.ev2_persons`.

The selected status profiles are copied to the runtime database. Home availability is derived from status `0`; EV1 charging-station availability is derived from status `2`. EV2 has no charging-station availability in this data. Runtime driving load is then calculated from each person's trip distances and the target vehicle's `consumption_per_km`, and distributed evenly over that person's driving periods. Charging limits and prices are assigned based on whether the vehicle is at home or, for EV1, at a charging station.

### Training selection

EV1 training includes all people whose VISTA household ID was not used for runtime. EV2 training selects 1,000 people from distinct VISTA households not used by runtime, using seed 42. The training database contains these status profiles (and the EV2 person mapping); runtime driving-load profiles are not created for training.

## 3.3 Rebuilding the database

The existing per-source steps can be run together from the repository root:

```shell
python src/ingestion/create_all_databases.py
```

The script rebuilds the intermediate files and databases as well as the final
runtime and training databases. It stops before changing databases if a
required starting input is missing. Use `--dry-run` to list the build steps
and check whether the starting inputs are available. The step-by-step flow is:

### Original dataset

Starting point: the project Excel workbook, configured by `EXCEL_FILE_PATH`.
The default in `src/runtime_config.py` is
`data/dataset_original/EC_EV_dataset.xlsx`.

1. `python src/ingestion/table_loading_original.py` reads the configured
   workbook using the sheet/range definitions in
   `src/ingestion/table_config.py` and creates `sqlite/source_original.db`.
   `table_config.py` is configuration imported by the loader, not a script to
   run separately.
2. `python src/ingestion/create_original_metadata.py` calculates the original
   load, PV, and EV metadata in `source_original.db`. The load metadata is
   needed for the CH candidate pool, PV metadata provides the runtime PV
   targets, and `initial_cp` is used for runtime load assignment.

### Load

Starting inputs: `data/dataset_CH_load/metadata.csv` and the household CSVs
under `data/dataset_CH_load/smart_meter_data/`. If that raw-data directory is
unavailable, `create_all_databases.py` uses the existing per-household CSVs in
`data/dataset_CH_load/smart_meter_data_filtered/` and skips the filtering step.

1. `python data/dataset_CH_load/filter_single_family_houses.py` filters
   metadata to single-family houses with at least 70,000 data points and none
   of the listed additional devices/changes. It copies matching CSVs to
   `smart_meter_data_filtered/` and writes `metadata_filtered.csv`.
2. `python data/dataset_CH_load/create_ch_database.py` combines those filtered
   CSVs into `sqlite/staging/CH_loads.db`, table `load`.
3. `python data/dataset_CH_load/create_metadata_table.py` calculates
   household-day statistics, keeping only complete days of 96 periods.
4. `python data/dataset_CH_load/create_valid_pool_table.py` requires
   `source_original.db` and its `base_load_metadata`. It creates
   `base_load_pool`, keeping days whose total energy and peak load are within
   the original data's ranges.
5. `python data/dataset_CH_load/select_ext_runtime_profiles.py` selects the
   250 runtime source days by contractual power range and writes
   `runtime_pool_by_cp`.

The runtime builder copies those 250 selected days into the 250 player
columns of `source_runtime.db.base_load`. The training builder excludes all
CH household IDs used in `runtime_pool_by_cp` and copies the full time series
of the remaining households to `source_runtime_training.db.load` to form the pool ofvalid training profiles.

### PV

`pv_data_raw.csv` is obtained using the link and search options in
[sauce](/data/dataset_DE_PV/sauce.txt). The unified script removes rows
without PV generation data and writes `data/dataset_DE_PV/pv_data_non_empty.csv`,
which forms the input for `create_pv_database.py`.

1. `python data/dataset_DE_PV/create_pv_database.py` converts cumulative
   readings to 15-minute kW values and creates
   `sqlite/staging/DE_pv_gen.db`, table `pv_gen`.
2. `python data/dataset_DE_PV/create_metadata_table.py` calculates complete
   system-day metadata.
3. `python data/dataset_DE_PV/create_valid_pool_table.py` creates
   `pv_gen_pool` from days with 46-54 active periods whose active window can
   be centered without moving it outside the day.
4. `python data/dataset_DE_PV/select_ext_runtime_profiles.py` creates
   `runtime_pool` from `residential3` pool days in 2018. This pool is required
   by the runtime builder.

The runtime builder assigns those days to the original PV target households,
reusing days if needed and multiplying generation by 0.8.
The training builder excludes `residential3`, keeps pre-2018 dates represented in
`pv_gen_pool`, and also multiplies values by 0.8. This results in the pv_gen table in the training db.

### EV

Starting point: `data/dataset_VISTA_EV/T_VISTA1218_V1.csv`.

1. `python data/dataset_VISTA_EV/create_work_commute_pairs_table.py` filters
   complete EV1 work-commute pairs and writes `work_commute_pairs.csv`.
2. `python data/dataset_VISTA_EV/create_ev1_database.py` turns those pairs
   into `sqlite/staging/VISTA_ev1_status.db`, including status, distances,
   and person-to-household mappings.
3. `python data/dataset_VISTA_EV/create_casual_commutes_table.py` filters
   EV2 casual-trip chains and writes `casual_commutes.csv`.
4. `python data/dataset_VISTA_EV/create_ev2_database.py` turns those chains
   into `sqlite/staging/VISTA_ev2_status.db`, including status, distances,
   and person-to-household mappings.

The two `create_*_metadata_table.py` scripts for VISTA calculate analysis
metadata; the runtime and training builders do not require those tables.
Runtime selection, copying the selected status profiles, and deriving EV
loads and availability are performed by `create_replacement_db.py`. Training
EV status tables are selected by `create_training_tables.py`.

### Final databases

After creating `source_original.db`, the CH and PV pools, the PV runtime pool,
and both VISTA staging databases, run:

1. `python src/ingestion/create_replacement_db.py` to copy the original
   database and replace its runtime profiles, creating
   `sqlite/source_runtime.db`.
2. `python src/ingestion/create_training_tables.py` to create
   `sqlite/source_runtime_training.db`. This step uses the runtime EV2
   household mapping to keep training households separate from runtime.

`create_all_databases.py` runs these steps in order. It overwrites the
generated source, staging, runtime, and training databases.
`sqlite/results.db` is not rebuilt; it contains simulation results rather
than source profiles.
