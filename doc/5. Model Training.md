# 5. Model Training

The XGBoost predictors forecast household base load, PV generation, and the availability status of both EVs. At each simulation step, the forecasts cover the rest of the day and serve as inputs to the MPC controller. The current models are untuned baselines.

We compare three forecasting approaches:

- **Recursive single-step.** A model predicts one step ahead and feeds its own predictions back as inputs to extend the forecast. Errors can accumulate during this rollout.
- **Multi-step with a shared model.** A single model predicts directly at selected horizons, using the horizon as an input feature. Interpolation fills the gaps between those horizons.
- **Multi-step with separate models.** Each selected horizon has its own model. Interpolation fills the gaps between their forecasts.

Historical averaging provides the baseline for assessing forecast accuracy and the effect of forecasts on MPC costs.

## 5.2 Data Split

The load feature generator assigns household IDs to disjoint splits using a fixed random seed. Five household IDs are reserved for test, five different IDs for validation, and all remaining IDs are used for training. It then deterministically samples 800 complete household-day profiles for training, 100 for test, and 100 for validation from the corresponding household pools. Dates may appear in multiple splits, but household IDs never do.

EV1 and EV2 use deterministic 80/10/10 splits by household ID. All profiles belonging to one household stay in the same split. In the current data, EV1 has 372 distinct households and EV2 has 1,000, so the split sizes are approximately 80/10/10. The EV2 features retain the source household ID in their `household_id` column.

PV reserves `residential3` for runtime and deterministically assigns two of the remaining three PV systems to training. The last training-eligible system is held out and its complete profile-days are randomly divided between test and validation. Those two splits therefore contain disjoint days but share the same PV system ID; evaluation does not measure generalization to a second unseen PV system.

Each generator writes Parquets to its `train`, `test`, and `validation` subdirectories under `training/features/feature_parquets/<dataset>/`. Model-training scripts read only `train`; validation guides feature selection and tuning, while test is reserved for the final comparison.

Load XGBoost tuning outputs are grouped under `training/tuning/load/`. Run `python -m training.tuning.pred_hypam_sweep` for the recursive single-step model; outputs go to `single_step/`. The sweep trains each parameter combination on `train` and selects the best by recursive forecast error on `validation`. On each held-out profile-day, it starts independent rollouts at timesteps 12, 24, 36, 48, 60, 72, and 84. Each rollout uses the actual profile history up to its start, then feeds its own predictions back into the runtime feature builder until the end of the day. It pools squared errors over all forecasted points for a profile-day, computes that day's RMSE, then averages the per-day RMSEs so each profile-day contributes equally. The table also includes next-step RMSE pooled over the first prediction from each rollout start, and the sweep saves per-start, per-step errors for the best validation model.

For direct forecasts, run `python -m training.tuning.pred_hypam_sweep --horizon 8`, replacing `8` with `16`, `32`, or `64`. These sweeps predict `y8`, `y16`, `y32`, or `y64` directly from the actual features at each forecast start; they do not roll predictions forward. They score only configured starts whose target remains within the same day: `step_8` uses starts 12–84, `step_16` uses 12–72, `step_32` uses 12–60, and `step_64` uses 12 and 24. Each horizon has its own output directory (`step_8/`, `step_16/`, `step_32/`, `step_64/`) and best parameters.

All sweeps use `train` for fitting and `validation` for selection; none reads `test`. After selecting parameters, evaluate once with `python -m training.tuning.pred_hypam_sweep --evaluate-test` for single-step, or add `--horizon 8` (or another supported offset) for a direct model. The chosen model is refit on `train` plus `validation` and evaluated on the held-out test profiles.

PV and EV tuning uses `python -m training.tuning.pv_ev_hypam_sweep --target pv`, `--target ev1`, or `--target ev2`. The sweep rebuilds model inputs with the runtime feature builders from each profile's history, rather than relying on precomputed features that may differ due to rounding (PV) or use whole-day commute boundaries (EV). PV has the same recursive single-step sweep as load and direct sweeps for t+8, t+16, t+32, and t+64; pass `--horizon 8` (or another supported offset) for a direct PV sweep. EV1 and EV2 use recursive single-step classification only. Their forecasts are discrete status classes (0, 1, or 2), and predicted classes are fed into subsequent steps. EV hyperparameters are selected by macro-F1 over all recursively forecast points; accuracy and balanced accuracy are reported as additional metrics. EV score rows are equally numerous per profile-day, so the pooled classification metrics give each profile-day equal weight. For all three targets, `--evaluate-test` performs the final test evaluation after validation selection, for example `python -m training.tuning.pv_ev_hypam_sweep --target ev1 --evaluate-test` or `python -m training.tuning.pv_ev_hypam_sweep --target pv --horizon 16 --evaluate-test`. Outputs are grouped under `training/tuning/pv/`, `training/tuning/ev1/`, and `training/tuning/ev2/`, with `single_step/` and PV `step_8/`, `step_16/`, `step_32/`, and `step_64/` subdirectories.
