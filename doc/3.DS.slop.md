# 3. Data acquisition and preparation

The project combines the original 250-household dataset with external load,
PV, and EV profiles. `household_id` is the project-wide name for a household
identifier. External source identifiers (such as VISTA's `HHID` and `PERSID`)
are retained where they identify the source household or person.

## 3.1 Original dataset and database tables

### Origin and format

The original dataset is the Excel workbook configured by
`EXCEL_FILE_PATH` (by default `data/dataset_original/EC_EV_dataset.xlsx`). It describes
250 households, 96 15-minute periods for one day, PV for 200 households, and
BESS for 150 households. `src/ingestion/table_loading_original.py` reads the
configured Excel ranges and writes the source tables to
`sqlite/source_original.db`. The original workbook is not currently present in
the repository checkout, so the sheet/range mapping below documents what the
ingestion code expects.

In wide time-series tables, `period` is 1-96 and columns `"1"` through `"250"`
are household IDs. The values in these original tables are loaded from the
workbook without resampling or profile selection. Tables created by the runtime
builder are described separately in the last column.

| Table | Format and content | Origin | Transformation / runtime handling |
|---|---|---|---|
| `base_load` | Wide; `period` plus 250 household columns; base electricity load | Excel `Load` sheet | Original values loaded as-is. Runtime values replaced with selected 96-period CH smart-meter days. |
| `bess` | Lookup; `household_id`, `model_id`, `capacity`, `charge`, `discharge`, `efficiency` | Excel `BESS` sheet | Technical attributes only. Initial/final SoC are not stored; simulation SoC comes from the scenario. |
| `buy_price` | Wide; household-specific grid purchase price by period | Excel `Buy Price` sheet | Loaded as-is and retained in runtime. |
| `sell_price` | Wide; household-specific grid feed-in price by period | Excel `Sell Price` sheet | Loaded as-is and retained in runtime. |
| `player_pv_bess` | Lookup; `household_id`, `has_pv`, `has_bess` flags | Excel `General Information` sheet | Loaded as-is and retained in runtime. |
| `fixed_costs` | Lookup; `household_id`, `fixed_costs` | Excel `Limits` sheet | Selects only the household ID and fixed-cost field; retained in runtime. |
| `initial_cp` | Lookup; `household_id`, `initial_cp` | Excel `Limits` sheet | Selects only the household ID and contractual-power level; used to assign a load profile. |
| `max_home_charge` | Lookup; `household_id`, `max_home_charge` | Excel `Limits` sheet | Renames `premium_charger_edp_capacity` to `max_home_charge`; retained in runtime. |
| `pv_gen` | Wide; PV generation by period and household | Excel `PV` sheet | Original values loaded as-is. Runtime PV is replaced with selected German PV days. |
| `ev1` | Lookup; EV1 technical, consumption, trip, and charging attributes | Excel `EVs` sheet, EV1 range | Loaded from the workbook and enriched with `charge_home`, `charge_station`, and `charge_slowest`; retained in runtime. |
| `ev2` | Lookup; EV2 technical, consumption, trip, and charging attributes | Excel `EVs` sheet, EV2 range | Loaded from the workbook and enriched with `charge_home`, `charge_station`, and `charge_slowest`; retained in runtime. |
| `ev1_at_home` | Wide; EV1 home availability by period | Excel `EV1 at Home (x)` sheet | Original values loaded as-is; runtime values derived from selected VISTA EV1 status (`status = 0`). |
| `ev1_at_charging_station` | Wide; EV1 away/charging-station availability by period | Excel `EV1 at Charging Station (x)` sheet | Original values loaded as-is; runtime values derived from selected VISTA EV1 status (`status = 2`). |
| `ev1_status` | Wide; combined EV1 status by period | Derived during Excel ingestion from the two EV1 availability tables | `1 - ev1_at_home + ev1_at_charging_station`; runtime status is replaced by VISTA commute profiles (0 home, 1 driving, 2 at work). |
| `ev1_load` | Wide; EV1 driving load by period | Excel `EV1 Load` sheet | Original values loaded as-is. Runtime load is recomputed from VISTA trip distance, driving periods, and each target EV's consumption rate. |
| `ev1_buy_price` | Wide; EV1 purchase price by period | Excel `EV1 Buy Price` sheet | Original values loaded as-is. Runtime price uses household grid price at home and the EV1 station tariff when away at a charging station. |
| `ev1_max_charge` | Wide; EV1 maximum charging/discharging power by period | Excel `Max EV1 Dis-Charge` sheet | Original values loaded as-is. Runtime values are derived from home/station availability and the household's applicable charge limits. |
| `ev2_at_home` | Wide; EV2 home availability by period | Excel `EV2 at Home (x)` sheet | Original values loaded as-is; runtime values derived from selected VISTA EV2 status (`status = 0`). |
| `ev2_at_charging_station` | Wide; EV2 charging-station availability by period | Excel `EV2 at Charging Station (x)` sheet | Original values loaded as-is; runtime is all zero because this EV2 data path has no station availability. |
| `ev2_status` | Wide; combined EV2 status by period | Derived during Excel ingestion from the two EV2 availability tables | `1 - ev2_at_home + ev2_at_charging_station`; runtime status is replaced by selected VISTA casual-commute profiles. |
| `ev2_load` | Wide; EV2 driving load by period | Excel `EV2 Load` sheet | Original values loaded as-is. Runtime load is recomputed from VISTA trip distance, driving periods, and each target EV's consumption rate. |
| `ev2_buy_price` | Wide; EV2 purchase price by period | Excel `EV2 Buy Price` sheet | Original values loaded as-is. Runtime price uses household grid price at home and is zero while away. |
| `ev2_max_charge` | Wide; EV2 maximum charging/discharging power by period | Excel `Max EV2 Dis-Charge` sheet | Original values loaded as-is. Runtime values are derived from home availability and the household's home charge limit. |
| `base_load_metadata` | One row per household; load statistics | Generated from `base_load` by `src/ingestion/create_original_metadata.py` | Calculates daily energy, maximum, standard deviation, load factor, peak period, morning/evening means, and `ramp_std`. Not copied into runtime. |
| `pv_gen_metadata` | One row per PV household; PV statistics | Generated from `pv_gen` by `src/ingestion/create_original_metadata.py` | Calculates energy, peak, variability, active-period bounds/count, and ramp metrics; excludes profiles with peak generation ≤ 0.05 kW. Not copied into runtime. |
| `ev1_metadata` | One row per household; EV1 trip/status statistics | Generated from `ev1`, `ev1_status` by `src/ingestion/create_original_metadata.py` | Summarizes trip count/distance, departure/arrival, driving/work/away periods. Not copied into runtime. |
| `ev2_metadata` | One row per household; EV2 trip/status statistics | Generated from `ev2`, `ev2_status` by `src/ingestion/create_original_metadata.py` | Summarizes trip count/distance, departure/arrival, and driving/away periods. Not copied into runtime. |

During Excel ingestion, `charge_home` is looked up from
`premium_charger_edp_capacity` in `Limits`. For each EV,
`charge_station` is `charge` when present, otherwise `station_max_charge`;
`charge_slowest` is the lower of the home and station rates (or the non-null
rate when only one is available).

`src/ingestion/create_replacement_db.py` starts `source_runtime.db` as a
SQLite backup of `source_original.db`, drops all `*_metadata` tables, then
replaces the runtime profile tables described above. It also creates
`ev2_persons` (`household_id`, `persid`, `HHID`) to preserve the selected
runtime EV2 person and source-household mapping. `source_runtime.db` is the
simulation input; simulation results are written to `sqlite/results.db`.

## 3.2 Household load profiles

### Source and staging format

Swiss smart-meter measurements are filtered to single-family houses without
the listed additional heating, EV, storage, or installation changes. Houses
must have at least 70,000 data points. The filtering is implemented in
`data/dataset_CH_load/filter_single_family_houses.py`.

`data/dataset_CH_load/create_ch_database.py` combines the filtered CSVs into
`sqlite/staging/CH_loads.db`, table `load`. Each CSV becomes a household
column; timestamps are 15-minute UTC timestamps and periods are numbered
1-96. The source `kWh_to_installation` value is multiplied by four to express
average power in kW for each 15-minute period.

`data/dataset_CH_load/create_metadata_table.py` computes daily metadata only
for complete days (96 non-null periods). `create_valid_pool_table.py` keeps
candidate days whose total energy and maximum load both fall within the
minimum-to-maximum ranges of the original household profiles.

### Runtime selection

The active runtime selection is created by
`data/dataset_CH_load/select_ext_runtime_profiles.py` in
`CH_loads.db.runtime_pool_by_cp`. It is **not** an unconstrained random draw:

1. Target counts follow the original `initial_cp` distribution: 152 at 3.45,
   80 at 6.90, and 18 at 10.35.
2. Candidate days must meet the maximum-load band for their target CP:
   `(2.30, 3.45]`, `(3.45, 6.90]`, or `(6.90, 10.35]` kW respectively.
   Candidates already passed the total-energy and maximum-load range filter.
3. The selection spreads the 250 target days over about 40 distinct CH
   household IDs. Higher-CP households are chosen first from IDs with the most
   eligible days; the remaining IDs are chosen by candidate availability.
   Per-ID day quotas are distributed across the CP groups.
4. `random.Random(42)` makes day selection and tie/order shuffling reproducible.
   The selected source day is then copied into that target household's
   `base_load` column without further scaling.

The separate `create_stratified_samples.py` implements an alternative
distribution-matched sample based on 2D quantile bins of original `max_load`
and `total_energy`. It is not the pool consumed by the current runtime builder.

### Training load

`src/ingestion/create_training_tables.py` builds the training `load` table
from the full CH time series. It excludes every CH household ID appearing in
`runtime_pool_by_cp`, preventing source households used for runtime from also
appearing in training.

## 3.3 Photovoltaic profiles

### Source and staging format

`data/dataset_DE_PV/create_pv_database.py` reads the German OPSD residential PV
CSV into `sqlite/staging/DE_pv_gen.db`, table `pv_gen`, with timestamps,
periods, and four source series (`residential1`, `residential3`,
`residential4`, `residential6`). The source values are cumulative meter
readings: consecutive readings are differenced and multiplied by four to
obtain kW per 15-minute period. Negative differences are clipped to zero and
the first difference is set to zero.

`create_metadata_table.py` calculates statistics for complete PV days,
omitting days whose maximum is at most 0.05 kW. `create_valid_pool_table.py`
keeps days with 46-54 active periods and shifts their active window, where
possible, to center around period 62. The resulting `pv_gen_pool` supplies
candidate dates.

### Runtime and training selection

`data/dataset_DE_PV/select_ext_runtime_profiles.py` creates the runtime pool
from all `residential3` candidate days in 2018, in date order (92 days in the
current staging database). Runtime insertion maps these days in order to the
200 households with PV in `source_original.db.pv_gen_metadata`, cycling
through the 92 days as needed. Each selected profile is multiplied by 0.8.
Although `pv_gen_pool` records `shift_periods`, the runtime insertion currently
does not apply that shift to profile values.

Training PV keeps pre-2018 dates present in `pv_gen_pool` for
`residential1`, `residential4`, and `residential6`; it excludes the
`residential3` runtime series. The retained values are also multiplied by 0.8.
This training table remains timestamped and wide rather than being reduced to
one day per household. The stored `shift_periods` are currently not applied to
the profile values in either runtime or training insertion.

## 3.4 Electric-vehicle profiles

### VISTA staging data

The VISTA CSV preprocessing scripts are in `data/dataset_VISTA_EV/`.
`create_ev1_database.py` turns complete work-commute pairs into a 96-period
wide `ev1_status` table plus person and trip-distance mappings.
`create_ev2_database.py` creates the casual-commute status, person, and
distance tables. EV statuses use 0 = home, 1 = driving, and 2 = away/at work.
EV1 status is wide (one column per person); EV2 status is long (`persid`,
`HHID`, `period`, `status`) because of its larger number of people.

### Runtime selection and profile creation

- **EV1:** `create_replacement_db.py` prioritizes people from shared VISTA
  household IDs, then fills the remaining 250 slots from other people.
  Selection/shuffling uses seed 42. A shared household can therefore
  contribute more than one person.
- **EV2:** candidates are shuffled with seed 42 and selected so that the 250
  runtime people have distinct VISTA `HHID`s. The selected mapping is stored
  in `source_runtime.db.ev2_persons`.
- For both EVs, status is copied from the selected VISTA person. Driving load
  is distributed evenly over that person's driving periods so total load
  energy matches trip distance times the target EV's `consumption_per_km`.
  Availability and EV charging prices/limits are then derived from status and
  the target household's technical rates.

### Training EVs

Training EV1 excludes every VISTA `HHID` used for runtime and retains the
remaining people. Training EV2 selects 1,000 people from distinct HHIDs that
are not used by runtime. Both status tables retain the 96-period wide,
simulation-facing format.

## 3.5 Build order

Run the relevant preparation steps when the source data changes:

1. Load the original workbook with
   `src/ingestion/table_loading_original.py`, then calculate original metadata
   with `src/ingestion/create_original_metadata.py`. These metadata ranges are
   used to define the load and PV candidate pools.
2. Filter CH households, create `CH_loads.db`, calculate daily metadata,
   create `base_load_pool`, and select `runtime_pool_by_cp`.
3. Create the German PV staging database, calculate metadata, create
   `pv_gen_pool`, and select the 2018 runtime pool.
4. Create the VISTA EV1 and EV2 staging databases.
5. Build the runtime database with
   `src/ingestion/create_replacement_db.py`.
6. Build training tables with `src/ingestion/create_training_tables.py`.

The training database `sqlite/source_runtime_training.db` contains:

| Table | Format and content | Origin and transformation |
|---|---|---|
| `load` | Timestamped wide CH load series | Full CH time series, excluding source household IDs used in the runtime pool. |
| `pv_gen` | Timestamped wide series (`residential1`, `residential4`, `residential6`) | Pre-2018 days in the PV candidate pool, excluding runtime series `residential3`; values scaled by 0.8. |
| `ev1_status` | Wide status matrix, 96 periods | VISTA EV1 profiles whose HHIDs are not used in runtime. |
| `ev2_status` | Wide status matrix, 96 periods and 1,000 training household columns | Seed-42 selection of people from distinct HHIDs not used in runtime. |
| `ev2_persons` | Lookup from training household ID to VISTA `persid` and `HHID` | Mapping for the selected 1,000 EV2 training profiles. |

The runtime and training database implementations are in
`src/ingestion/create_replacement_db.py` and
`src/ingestion/create_training_tables.py`. The preparation and selection
scripts referenced above live under `data/dataset_CH_load/`,
`data/dataset_DE_PV/`, and `data/dataset_VISTA_EV/`.
